Telemetry queries used in this project
SQL + Kusto
SQL — Identify tenants still on deprecated API version
-- Find all tenants making Synapse REST v2 calls in last 30 days SELECT t.tenant_id, t.org_name, t.subscription_tier, t.region, COUNT(a.call_id) AS api_calls_30d, MAX(a.timestamp) AS last_seen, m.migration_pct FROM api_usage a JOIN tenants t ON a.tenant_id = t.tenant_id LEFT JOIN migration_status m ON m.tenant_id = t.tenant_id WHERE a.api_version = 'synapse-rest-v2' AND a.timestamp >= DATEADD(day, -30, GETDATE()) AND m.migration_pct < 100 GROUP BY t.tenant_id, t.org_name, t.subscription_tier, t.region, m.migration_pct ORDER BY api_calls_30d DESC;
SQL — Segment by migration urgency
SELECT tenant_id, org_name, DATEDIFF(day, GETDATE(), eol_date) AS days_to_eol, CASE WHEN DATEDIFF(day, GETDATE(), eol_date) <= 14 THEN 'CRITICAL' WHEN DATEDIFF(day, GETDATE(), eol_date) <= 30 THEN 'HIGH' WHEN DATEDIFF(day, GETDATE(), eol_date) <= 60 THEN 'MEDIUM' ELSE 'LOW' END AS urgency_tier FROM migration_status WHERE migration_pct < 100 ORDER BY days_to_eol ASC;
Kusto (KQL) — Azure Monitor: active Synapse workspace query
// Pull tenants with Synapse activity in last 30 days via Azure Monitor logs AzureDiagnostics | where TimeGenerated >= ago(30d) | where ResourceType == "MICROSOFT.SYNAPSE/WORKSPACES" | where OperationName has_any ("Pipeline", "SparkPool", "SQLPool") | summarize TotalOperations = count(), LastSeen = max(TimeGenerated), UniqueOperations = dcount(OperationName) by SubscriptionId, ResourceGroup | where TotalOperations > 0 | order by TotalOperations desc | project SubscriptionId, ResourceGroup, TotalOperations, LastSeen, UniqueOperations
Kusto (KQL) — Compare Synapse vs Fabric adoption per tenant
// Track migration velocity: old vs new platform API calls AzureDiagnostics | where TimeGenerated >= ago(7d) | where ResourceType in ( "MICROSOFT.SYNAPSE/WORKSPACES", "MICROSOFT.FABRIC/CAPACITIES" ) | extend Platform = iff( ResourceType has "SYNAPSE", "Synapse", "Fabric" ) | summarize Calls = count() by SubscriptionId, Platform, bin(TimeGenerated, 1d) | order by TimeGenerated desc

Deprecation & migration playbook
v2.1
Structured process for handling customer migrations at scale
01
Telemetry pull — identify active users
Run the KQL query in Azure Monitor daily to identify tenants with active Synapse API usage. Export results and cross-reference with migration_status table. Flag any tenant with last_seen < 7 days as high-priority.
tool: Azure Monitor · schedule: daily · owner: PM / Data Eng
02
Urgency segmentation
Use SQL query #2 to segment all remaining tenants into CRITICAL / HIGH / MEDIUM / LOW based on days to EOL and migration completion %. CRITICAL tenants (<14 days) require same-day outreach escalation.
tool: Azure SQL · output: prioritised outreach list
03
Personalised outreach — first contact
Send migration notice referencing actual usage data (API calls, pipeline runs). Attach Fabric migration guide. Include specific EOL date and offer FastTrack engineer assignment. Do not send generic emails — reference tenant-specific telemetry to increase response rate.
channel: email + Azure portal banner · SLA: 48h response target
04
Response tracking & follow-up cadence
Log all customer responses in CRM. For non-responders: Day 3 → follow-up email. Day 7 → escalate to account team. Day 12 → final warning with portal banner. If still no response at D-7 to EOL, trigger mandatory escalation workflow.
tool: CRM + internal ticketing · owner: PM + CSM team
05
Migration validation
After customer confirms migration, verify via telemetry that Synapse API calls have dropped to zero and Fabric API calls have increased proportionally. Update migration_status table. Only close the ticket once both conditions hold for 3 consecutive days.
tool: KQL query #4 · validation period: 3 days
06
Post-migration support window
Keep FastTrack engineer available for 30 days post-migration. Monitor for regressions. Collect feedback to improve playbook. Update documentation based on common blockers encountered.
owner: FastTrack team · duration: 30 days post-migration
Why I built this

At Accenture, I worked on mission-critical data operations and saw firsthand how difficult it is to manage large-scale platform migrations without a single source of truth. When I came across the Azure Data deprecation and customer migration challenge, it mapped almost exactly to problems I'd dealt with — just at a much larger scale.

I built this tool to think through the problem operationally: how do you identify which customers are most at risk? How do you communicate the right message at the right time? How do you measure whether outreach is actually working?

The SQL and KQL queries are real and designed to work against Azure Monitor / Azure SQL. The playbook is written from scratch based on how deprecation programs actually work at cloud scale.
